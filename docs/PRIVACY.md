# 公开网站与内部客户库边界

## 为什么需要分开

GitHub Pages 网站和公开 GitHub 仓库中的文件可以被任何访问者下载。把文字在页面上折叠、隐藏或不显示，并不能保护源文件里的个人信息。

本项目同时包含“市场情报展示”和“销售获客”两类用途，应采用两套数据层：

- 公开层：支持市场判断、竞品分析和渠道分布展示；
- 内部层：支持 KP 联系、销售评分和跟进管理。

## 公开层允许的数据

- 公司法定名称和品牌名称；
- 公司官网及公开伙伴页面；
- 官方办公地址和公开总机；
- `sales@`、`info@` 等公司通用邮箱；
- 公开可验证的产品、代理、分销或集成关系；
- 来源链接、核验日期和证据状态；
- 只到职位类型的 KP 信息，例如“采购负责人”或“产品经理”。

## 内部层数据

- 个人姓名与个人邮箱的组合；
- 手机号码和即时通讯账号；
- LinkedIn 等个人社交账号；
- 采购负责人、老板、产品经理等具体联系人名单；
- 联系优先级、合作意向、沟通记录和下一步行动；
- 海关数据推断出的客户线索和内部判断；
- 未经公开来源明确允许再次发布的数据。

内部文件应放在仓库外，或放在已被 `.gitignore` 排除的 `private/`、`data/private/` 目录中。更稳妥的长期方案是使用私有 Excel、Airtable、CRM 或私有数据库，以 `company_id` 与公开网站连接。

## 发布前检查清单

1. 这条信息是否必须公开才能支持市场结论？
2. 联系方式是公司通用联系方式，还是可识别个人的联系方式？
3. 来源是否允许公开引用或再分发？
4. 是否记录了证据链接与最后核验日期？
5. 历史关系是否被明确标记，而不是写成当前代理关系？
6. 是否把“潜在合作对象”误写成“已验证经销商”？

## 关于仓库中已经存在的信息

从当前页面删除内容，并不一定会从 Git 历史版本中删除。如果确认已有个人信息不应公开，需要单独执行以下治理流程：

1. 先把内部业务需要的数据安全迁移到私有位置；
2. 从当前公开页面和数据文件中删除或替换；
3. 检查 Git 历史和 GitHub Pages 缓存；
4. 根据组织政策决定重写历史或迁移到新的干净公开仓库；
5. 重新核验公开网站中只剩允许公开的数据。

历史清理会改写版本记录，必须在获得项目负责人确认和完成备份后进行。
